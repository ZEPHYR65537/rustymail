## 1. 发现、修复与保留项

| 复查项 | 本轮处理 | 验证与限制 |
| --- | --- | --- |
| R1：取消写入提前释放额度和实例锁 | 文件、实际阻塞工作、清理与准备凭证共同持有资源 | 卡住阻塞线程后取消 append/prepare，额度与锁保留；另在已同步文件的准备工作中取消，只留下孤儿，无接受记录 |
| R2：已读撤销通知在查询取消后丢失 | 会话保存 pending，检查完成才清除 | 消费通知后取消查询，不再发送新通知也会检测到失效身份；最终接受事务复查保留 |
| R3：100 条合法凭据响应超过 16 KiB | 请求/响应分别限 16/64 KiB，发送端有界序列化 | 最大转义标签和整数字段往返；超限拒绝且不发送残帧；Linux 真实管理客户端读取整页 |
| DATA 每行重复分配 | 单个可复用 decoder，借用完整帧，点透明推进切片 | 保留所有分片、CRLF、NUL 和行长校验；分帧微基准单独报告 |
| 慢日志和文件清理阻塞网络线程 | 有界后台诊断日志；清理持有额度转交阻塞线程 | 慢日志测试检查满队列丢弃与计数；诊断日志可能丢失，不能作为持久接受账本 |
| Argon2 参数组合超过目标机内存 | 配置内存乘并发不超过 256 MiB | 默认两路共 128 MiB；组合边界测试；不等于总 RSS 或 cgroup 压力验收 |
| 每次认证都扫描速率表 | 全表清理最多每秒一次，命中的记录独立到期 | 测试验证账号窗口不会等待下一次全表扫描；表满时对新键采取保守拒绝 |
| 重复通道代码与过长认证分支 | 普通调用复用 owner 通道，SASL 对话独立模块，CLI 单线程调度 | 接受提交保留结果不明的专用语义；没有改动数据库 schema 或权限策略 |
| 启动与 GC 全量正文散列 | 保留，并在教程明确成本 | 流式内存不代表恒定时延；快速启动与后台有界校验仍待设计及故障验收 |

新增 8 项 Rust 测试，其中一项同时覆盖写入/准备两个排队取消分支；另在原配置测试中增加总内存组合边界。源码和取消原理见[教程](../../docs/13-cancellation-and-bounds.md)。

## 2. 跨平台与独立客户端

Rust 1.94.0；Linux 53 项、Windows 49 项测试通过。两平台格式、严格 Clippy、构建、原有 SMTP 收信/重启/恢复/维护客户端通过。

- [Linux 协议记录](linux-protocol.json)：12 组，含新增的 100 条最大标签响应、不同 UID 拒绝、DATA 撤销、账号禁用和证书轮换。
- [Windows 协议记录](windows-protocol.json)：8 组；不冒充 Unix socket 验证。
- 两份报告均记录被测 revision，且 `working_tree_dirty=false`。[证据出处](ci-provenance.json)记录 artifact ID、下载压缩包与归档文件的 SHA-256。Windows 输出只规范化换行，不改变 JSON 值。

新增分页夹具仅在一次性测试数据库离线建立，复用已有测试 PHC，不处理真实邮箱或密码。运行时权限策略和凭据创建 API 没有为测试放宽。

## 3. 断电、磁盘满和性能证据

[存储故障原始结果](storage-regression.json)覆盖 11 个断电位置及两个真实磁盘满场景。已接受邮件保留，正文缺失/损坏、配额、UID 和投递关联均无不一致；准备后未提交的正文可留下孤儿。包括收到最终 250 后断电，以及迁移、GC 的断电恢复。

环境为 QEMU 8.2.2、客体 Linux 6.8.0-139、512 MiB RAM、2 vCPU、128 MiB ext4 专用镜像。故障模型是杀死 QEMU 丢弃客体内存，宿主机和存储仍存活；不声称覆盖物理掉电。

[匿名 SMTP 基准](linux-benchmark.json)在 AMD EPYC 7763 CI 主机运行，守护进程绑两核，release、WAL/FULL、16 KiB 缓冲。时延从 MAIL 到最终 250，复用连接；下列为本次短期样本：

| 实际正文大小 | 并发 / 封数 | 吞吐（封/秒） | p99（ms） | 守护进程 VmHWM（KiB） |
| --- | --- | --- | --- | --- |
| 958 B | 1 / 100 | 487.24 | 4.79 | 7704 |
| 65518 B | 1 / 100 | 310.01 | 5.63 | 7596 |
| 65518 B | 4 / 100 | 667.87 | 7.73 | 7820 |
| 26214398 B | 1 / 4 | 2.75（68.67 MiB/s） | 367.62 | 7472 |

这不是生产负载：没有 TLS/认证/扫描/外发，不包含 Python 发生器内存，没有施加 2 GiB 总内存限额。历史 M1 数据来自不同主机，不能直接据此计算版本加速比。25 MiB 场景只有四封，p99 是该小样本中的最大值，不能替代尾延迟压力报告。

[分帧原始样本](linux-framing.json)比较同一二进制的拥有缓冲与借用 API。每种行长约 16 MiB，四轮交替顺序，以下取中位数：

| 含 CRLF 的行长 | 拥有缓冲（ms） | 借用缓冲（ms） |
| --- | --- | --- |
| 2 B | 298.44 | 96.56 |
| 80 B | 35.46 | 32.14 |
| 1000 B | 28.77 | 29.96 |

空行场景约快 3.09 倍，80 字节行有较小收益，1000 字节行本次约慢 4%。这个实验没有分离循环/函数分支/校验开销，也没有统计分配次数，不能声称所有输入都提速。它支持“消除大量短行的重复分配”，不支持端到端吞吐提升 3 倍的说法。旧版本多余的下一行缓冲分配已从拥有缓冲 API 中移除，此处不是完整旧版/新版对比。

## 4. 依赖与兼容性

Cargo.lock 只改变四个工作区包的版本，153 个第三方包没有增删或升级。使用 cargo-audit 0.22.2 和此前同一份 RustSec 快照 `bd8037e5cbb8d8cc687c68cdd42ca53d742503fb`，读取 1256 条公告，已知漏洞和警告均为零。[原始审计及锁文件摘要](rustsec-audit.json)

审计采用 `--no-fetch --no-yanked`，不包含撤回版本检查，也不证明依赖没有未知漏洞。代码仍禁止本项目 Rust 模块中的 unsafe；这不能替代 SQLite、TLS 等依赖及底层平台的安全性验证。

无需数据迁移或更改默认配置。此前允许的过大 Argon2 配置现在启动校验失败；若调低上限，超出上限的已有 PHC 仍按原策略拒绝验证，应先规划凭据轮换。在线管理须使用同版 CLI，旧客户端仍可能拒绝大于 16 KiB 的响应。

诊断日志现在可能在拥塞时丢弃。`logs_dropped` 反映恢复后观测到的损失，强杀或永久堵塞时可能连该事件也无法输出。持久操作状态以数据库为准。

## 5. 生产验收边界

测试使用环回、合成邮件、临时证书和一次性存储。没有完成大存量启动/GC 时延、TLS/认证混合压力、长期取消洪峰或 cgroup 总内存限额验证。IMAP、完整 SMTP 接入、外发、域认证和反垃圾仍按后续里程碑推进；这些修复不解除 L0 限制。
