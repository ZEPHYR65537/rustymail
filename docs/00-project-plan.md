# 落地设计总纲

## 1. 产品和学习目标

最终得到两个相互验证的成果：一个能在明确边界内生产运行的 Rust 邮件服务器，以及一套可以从实验追踪到实现和测试的网络编程教材。教学代码就是实际服务的代码；没有一份省略错误处理的“教学版”假装等同于生产实现。

开发优先级依次为：不丢已确认邮件、身份和权限正确、协议互通、可运维、资源有界、性能优化。优先级不表示性能不重要，而是防止通过减少同步落盘、跳过鉴权等方式制造漂亮但无意义的吞吐数字。

本轮先交付设计，不声称已经完成服务器。后续每一阶段均更新能力表、源码链接、运行证据和已知限制。真实部署需要域名、VPS、证书与测试账号；这些外部资源尚未提供，不应编造公网验收结果。

## 2. 完整范围和首发边界

| 能力 | 完整项目目标 | 边界与验收 |
| --- | --- | --- |
| 入站 SMTP | 自研 25 端口服务、真实本地收件人验证 | 匿名客户端只能向已配置的本地域投递 |
| 用户提交 | 自研 465；587 为兼容入口 | TLS 内认证，账户只能使用授权发件地址 |
| 出站 | 自研持久队列、SMTP 客户端、重试、退信 | 先固定中继，再直接 MX；逐收件人记录结果 |
| IMAP | 自研 IMAP4rev1 核心及选定扩展 | 993，Gnus 和第二个独立客户端互通 |
| 持久化 | SQLite 元数据 + 不可变邮件文件 | 故障注入证明确认后的数据可恢复 |
| 账号管理 | 本地账户、可撤销应用密码、配额 | 密码使用 Argon2id；管理默认只走 Unix socket |
| 域认证 | DKIM 签名/验证、SPF、DMARC | 使用库，自己实现预算、调用顺序和策略 |
| 反垃圾 | 接入 Rspamd 的扫描决策 | 公网入站生产配置默认要求扫描；扫描故障临时拒收 |
| 运维 | 队列检查、恢复检查、导入导出、备份、指标 | 备份恢复演练是上线前提 |
| Emacs | Gnus + 内置 smtpmail + auth-source | 收发、附件、已读、文件夹、Sent 与失败恢复 |

首发只创建 ASCII local-part 邮箱。域名做规范化；需要国际化域名时显式使用经过验证的 IDNA 库。中文显示名、中文主题、正文和附件仍可使用 MIME。首发不宣告 SMTPUTF8，不把“不支持国际化信封地址”误写成“不支持中文邮件”。

首发不做：多机共享 SQLite、跨地域复制、Webmail、JMAP、POP3、邮件列表、自动外部转发、Sieve、OAuth 身份提供方、日历联系人、端到端加密服务器托管。它们可以扩展，但不是这轮设计中已经解决的功能。

首发支持多域但只允许同一管理边界内的邮箱；不是多租户托管平台。全局去重与全文搜索索引也暂不实现，以避免早期引入隐私侧信道、GC 竞争和索引写放大。

## 3. 三种运行等级

| 等级 | 适用场景 | 开放条件 |
| --- | --- | --- |
| L0 实验 | 环回地址、测试证书、合成邮件 | 不公开端口，不承载唯一真实邮件副本 |
| L1 单机生产 / 中继出站 | 真实入站、IMAP、自研队列经固定上游发信 | M0–M7 全部完成、恢复和安全验收通过 |
| L2 单机生产 / 直接出站 | 服务器自己查询 MX 并直投 | 另需 M8，PTR、IP 信誉、MTA-STS 和实际互通验收 |

L1 仍然是自行实现服务器，上游只承担下一跳传输。L1 不算完整直接投递目标完成；最终交付要求 L2。未实现的功能必须在 capability、CLI 和文档中一致地不存在。

## 4. “生产可用”的可检验定义

- DATA 结束后的成功响应意味着消息内容及收件人责任已经耐久提交。机器异常退出不应使它成为幽灵邮件。
- 外部网络只提供至少一次语义：最终响应丢失时可能重复。不得宣称互联网邮件端到端 exactly-once。
- 重试队列、原文、账号和邮箱状态都能从一致备份恢复；明确单机磁盘彻底损坏时仍受备份 RPO 约束。
- 无开放中继、无未加密登录、无任意文件读取、无未授权邮箱访问；限制 CPU、内存、磁盘、DNS 和任务数量。
- 支持证书轮换、账户撤销、进程重启、升级回滚和人工调查，操作不依赖直接修改生产数据库。
- 有可复现负载结果和 72 小时稳定性报告；重要安全问题关闭；兼容性、故障矩阵、恢复演练留档。

单机目标不包含高可用 SLA。计划容量只适用于测量过的邮件大小、并发、磁盘与扫描组件配置。

## 5. 技术选型

| 领域 | 首选 | 采用理由 / 验证重点 |
| --- | --- | --- |
| 网络运行时 | Tokio、tokio-util、bytes | 异步 I/O、定时器、取消；所有队列和任务须有预算 |
| TLS | rustls、tokio-rustls | 不自写密码协议；明确 crypto provider 和证书验证模式 |
| SMTP 语法 | smtp-proto | 作为解析器候选；服务端状态和资源限制由本项目负责 |
| IMAP 语法 | imap-codec、imap-types | 编解码候选；必须先验证 literal 是否可有界处理 |
| MIME | mail-parser | 提取语义和结构；不假设全量解析天然是流式或低内存 |
| 域认证 | mail-auth | DKIM、SPF、DMARC；验收所选版本对新规范的实际支持 |
| 口令 | RustCrypto argon2、password-hash、系统随机数 | PHC 参数随散列存储，限流后才做昂贵验证 |
| 数据库 | rusqlite + 明确锁定的 SQLite | 专用线程，短事务；WAL 与 FULL 同步 |
| DNS | Hickory Resolver 候选 | 连接到受控递归解析器；缓存、并发、超时可控 |
| 配置和管理 | serde、toml、clap | 严格拒绝未知字段；配置验证与业务启动分离 |
| 观测 | tracing、Prometheus 文本指标 | 有界标签，无正文和密码日志 |
| 测试 | proptest、cargo-fuzz、Criterion、独立客户端 | 状态机、异常边界、端到端和真实持久化验证 |

这些是选型，不是已锁定版本。M0 应核验许可证、MSRV、维护状况和安全公告，生成 `Cargo.lock`、工具链文件、依赖清单和离线构建材料；禁止用未检查的 `latest` 作为发布依据。库的源码与官方文档入口见[参考资料](09-decisions-and-references.md)。

SMTP/IMAP 解析器并不等同于完整服务器。若候选库要求整封 APPEND literal 进内存，M0 的结论应是更换或扩展适配层，不能删掉资源约束。成熟组件降低重复劳动，但错误的调用方式依旧会造成漏洞。

## 6. 学习成果如何随代码产生

每个模块至少提供“问题 → 协议或系统原理 → 最小实验 → 真实实现 → 失败案例 → 验收”的完整链条。每次修复跨层问题新增知识记录，例如：TLS 升级为什么必须丢弃预读明文、异步取消为何不等于事务回滚、UID 为什么不是消息序号。

所有性能结论给出硬件、版本、命令、输入分布、并发、延迟分位数和错误率；所有设计变更记录替代方案与代价。先读[教程路线](06-learning-guide.md)，再按[实现计划](07-implementation-plan.md)动手。
