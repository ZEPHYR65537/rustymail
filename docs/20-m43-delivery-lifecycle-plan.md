# M4.3 实施计划：让每项投递责任都有后续处理

状态：四个子步骤已在 0.10.0 实现，逐项证据见 [M4.3 报告](../reports/m4.3/validation.md)，设计取舍和可执行操作见[第 22 章](22-m43-delivery-lifecycle.md)。本页保留原始范围与退出条件；生产入口继续关闭，本阶段完成也不等于整个服务器可生产使用。

## 1. 用户可见目标

提交一封发给多个收件人的邮件后，成功者保持成功，临时失败者按原策略重试，明确永久失败或已到期者产生可查询的失败通知。结果不确定时明确保留人工处理责任，不自动重发，也不谎报“对方没有收到”。通知自身失败不能生成无限退信。

按四个子步骤实施，每一步同时交付代码、独立实验、教程与操作说明。

## 2. M4.3a：终态与通知事务

- 先列出 pending、leased、deferred、uncertain、delivered、failed、hold 的完整转移表，区分传输失败、内容损坏、上游配置故障、人工暂停和到期。失去最终回复仍是 uncertain；普通 pending/deferred 到期才进入明确的失败处理，不能把未知结果按超时改成确定未送达。
- 使用现有 `notification(delivery_id, kind)` 唯一键，建立“原投递失败—通知邮件—通知投递责任”的关联。初版每个失败收件人一份通知，避免等待其他收件人终结，也避免把其他收件人地址放入本份状态报告。
- 通知正文先按既有文件发布顺序持久化，再在同一 SQLite 事务中提交最终失败、notification、通知 message/delivery 及必要的本地 UID/配额。若先前已经记录 failed，则事务负责补齐未通知责任。重跑不能生成第二份相同通知。
- 写满磁盘、通知目标配额满或事务失败时不删除原信，不虚报“已通知”；保留可扫描的未通知责任。每次扫描、生成字节数和并发均设上限，避免故障期间无限生成通知或阻塞收信。
- 历史方案曾要求每次结构变化增加迁移；2026-10-08 起改为首次正式发布前直接维护一份当前结构，拒绝不兼容实验库。事务、持久性和故障恢复实验仍然保留，见[第 23 章](23-simplicity-and-invariants.md)。

验收：在通知文件同步后、数据库提交前后、结果返回前分别强杀或注入错误；重启后每个失败收件人最多对应一项持久通知责任，无丢失引用和重复本地交付。“事务内至多一份通知”不保证远端网络恰好收到一次，通知的远端发送仍遵循 uncertain 策略。

## 3. M4.3b：DSN 格式与循环保护

- 生成 `multipart/report; report-type=delivery-status`，包含有限的人类可读说明与 `message/delivery-status`；填写 Reporting-MTA、Final-Recipient、Action 和 Status。可选诊断只使用有界、经过清洗的内容，不插入原始任意上游文本。
- 通知发往原始 SMTP reverse-path，而不是邮件头 From；通知自身使用空信封发件人 `MAIL FROM:<>`。原邮件为空 reverse-path 或 source=dsn 时，不再生成失败 DSN，改为记录管理员可查询的失败。
- 本阶段自动通知以已认证 submission 的既有责任为主要端到端路径；内部生成和离线导入来源必须显式定义资格。不会为匿名入站被拒绝的邮件另发退信，也不会以任意伪造头部为目的地址。
- 初版省略可选的原文附件，防止泄露 Bcc、认证信息和不必要的正文；不给每份报告复制其他收件人的失败列表。每份报告建议硬上限 16 KiB，并纳入统一暂存／队列预算。
- 用明确的状态映射表记录增强状态码；未能确定细分类别时采用适当通用类别，不编造对方的精确故障原因。自动成功通知、延迟通知，以及 RFC 3461 的 NOTIFY/RET/ENVID/ORCPT 协商另行排期；只生成失败 DSN 不足以宣告支持 `DSN` 扩展。

格式、状态码和空 reverse-path 规则分别依据 [RFC 3464](https://www.rfc-editor.org/rfc/rfc3464)、[RFC 3463](https://www.rfc-editor.org/rfc/rfc3463) 与 [RFC 5321 §4.5.5](https://www.rfc-editor.org/rfc/rfc5321#section-4.5.5)。具体字段及映射实现时逐条建立规范到测试的对应。

验收：用独立 MIME 解析器检查字段、CRLF 和内容；覆盖永久拒绝、多收件人部分失败、空 reverse-path、通知本身投递失败、超长诊断和隐私字段。所有实验使用临时账号与环回对端。

## 4. M4.3c：到期、不确定结果与操作记录

- 将 due 调度与 expiry 扫描分开，使用有界分页及合适索引，避免 next_attempt 很晚的任务错过到期处理。可控时钟测试覆盖到期边界及壁钟异常，保持现有时钟保护。
- 让 `queue show/list` 展示原投递、通知责任及未通知原因。管理操作记录选择了哪个 delivery、原状态、目标状态和重复投递风险；不能只留下一个全局重试开关。
- uncertain 不自动重发；显式重试继续要求承认重复风险。人工将其结案必须记录依据，且不能在没有送达证据时标为 delivered。已通知的终态不会被普通 retry 擦除；再次发送应建立可追溯的新责任。
- hold 需区分人工暂停和本地故障，提供修复后恢复的方法；通知无法进入本地满配额邮箱时仍保持待处理，可在释放配额后恢复。
- 本阶段不自动删除已接受原文和投递历史；先把逻辑终态与物理回收区分清楚。历史保留期限、备份 pin 与垃圾回收的完整联动仍属后续容量／运维工作。

验收：部分成功者不会因其他收件人失败而重发；到期恰好建立一项通知责任；uncertain 跨重启不变；通知生成临时失败后能够恢复；扫描不会因大批 hold 或远期任务无限占用 owner。

## 5. M4.3d：PIPELINING 与中继故障互通

- 接收端只有在合并／分片命令、逐条有序回复和 DATA 边界验证通过后才宣告 PIPELINING。
- 发送端仅在当前 TLS 会话重新 EHLO 确认能力后使用流水线；先在现有单收件人连接模型中流水化 MAIL/RCPT/DATA，按发送顺序收集有界回复，明确处理 MAIL 或 RCPT 被拒绝而后续命令已发出的情况。拿到有效 354 且前置成功后才发正文。
- 对端不支持时保持顺序发送；STARTTLS、AUTH 和正文结束处保留各自同步边界，不把明文阶段读到的能力带入 TLS。
- 此步骤不要求实现连接池或跨收件人合并发送。它们会改变故障与租约粒度，另有测量和设计成本。

依据 [RFC 2920](https://www.rfc-editor.org/rfc/rfc2920)；验收覆盖逐字节回复、合并回复、前置失败、421、错误数量／格式、部分写入、取消、TLS 能力重置和最终回复丢失。继续保持回复长度、时间、内存及并发边界。

## 6. 整阶段退出条件

| 责任 | 必须观察到的结果 |
| --- | --- |
| 本地／远端混合提交 | 一次接受，多条责任独立推进；永久失败仅通知相应收件人 |
| 原子通知 | 强杀后没有重复通知记录，没有指向未持久化正文的元数据 |
| 通知失败 | 空发件人循环被截断；失败责任仍可查询 |
| 到期与未知结果 | 确定到期有通知；未知结果不会被伪装为确定失败或自动重发 |
| PIPELINING | 宣告与实际能力一致；拒绝、断连、TLS 重置不串事务 |
| 资源与恢复 | 有界生成／分页；磁盘满、配额满可恢复；不增加整信缓冲 |
| 工程证据 | Windows/Linux 单测和独立对端通过；Linux 强杀／存储故障有原始报告；依赖审计通过 |
| 教程与操作 | 解释事务 outbox、EOF/确认边界、不确定性、退信循环和按序回复；提供可执行排错步骤 |

Linux 遗留管理 socket 的受控清理仍必须如实记录，不能用测试脚本清理代替生产自动恢复。M5 才实现 IMAP 和 Emacs 完整收信／Sent 归档互通；公网策略与生产运维仍受 M6/M7 门槛约束。
