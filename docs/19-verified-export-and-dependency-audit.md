# 从两项审计缺口学习：校验读取与持续依赖审计

0.10.0 增补：CI 的空缓存环境暴露了 cargo-audit 0.22.2 的一个验收陷阱：部分 yanked 查询缺少索引条目时，stderr 报错但进程仍可退出成功。现有安全工作流先 `cargo fetch --locked`，再保留并拒绝非空审计 stderr；“任务绿色”和“公告零漏洞”不能单独证明撤回版本检查完整。实例和修复证据见 [M4.3 报告](../reports/m4.3/validation.md)。

本章对应 M4.2 后的审计修复。学习目标是区分“成功复制字节”与“读到了承诺保存的邮件”，以及“锁文件固定”与“依赖目前没有已知漏洞”。它们分别涉及运行时数据完整性和随时间变化的外部知识。

## 1. 反例先于修复

旧 `Store::export` 检查账户归属、文件路径和类型，然后调用 `io::copy`。若文件被等长篡改，复制没有任何 I/O 错误；若文件截断，复制也会正常读到 EOF。两种情况都曾使 CLI 输出成功，而 `check-store` 能发现数据库记录与文件不符。

这里的根因不是 SHA-256 算法缺失：队列发送已有摘要校验。问题是两个读取入口提供了不同的保证。独立的完整性检查也不能替代当前读取的校验，因为管理员未必先运行检查，文件也可能在两次操作之间发生变化。

## 2. 把成功定义在 EOF，而非最后一次 write

现在 [VerifiedReader](../crates/store/src/verified.rs) 对每个实际读取的块更新长度与 SHA-256，超过记录长度立即报错，读到 EOF 时核对总长度和摘要。空缓冲区的 `read` 可以返回 0，但不会设置“已校验”状态。完整性失败后，后续非空读取继续失败。

导出和队列都调用这一层。它不持有整封邮件；哈希状态和复制缓冲不会随正文长度增长。代价是导出时对全部字节计算一次 SHA-256，不能再把无需校验的内核文件复制当作等价实现。数据库中的摘要是这里的可信依据；同时修改数据库与文件的攻击不由这种校验解决。

[QueuedReader](../crates/store/src/queue.rs) 仍单独持有租约 guard，所以抽取共同代码没有缩短实例锁和并发令牌的生命周期。SMTP 仍然在校验 EOF 成功后才发送 DATA 终止符；不能为了提前结束网络传输而绕过末尾校验。

## 3. 流式校验不代表原子输出

等长篡改可能直到 EOF 才被发现，此时 `Write` 目标已收到部分甚至全部字节。`Store::export` 的契约因此是：返回 `Ok` 才能确认内容完整，返回错误时调用方必须丢弃不可信输出。向不可撤销的网络流写入时，调用方要设计自己的确认边界，不能把错误返回当成撤回已发送字节。

[CLI](../crates/server/src/cli/control.rs) 用 `create_new` 创建输出，避免覆盖原文件；只有流式校验及文件 `sync_all` 成功后才打印成功记录。复制、校验或同步失败时，关闭文件并尝试删除本次产物。文件系统拒绝删除或进程遭强杀时仍可能留下文件，因此“文件存在”不是成功凭据；这次修复也不承诺目录项在断电后持久化。需要跨崩溃的原子发布时，应另做同目录临时文件、同步和发布协议。0.9.0 将管理实现移至该共享模块；当前统一使用 `rustymail admin`。

可复现实验：

```sh
cargo test -p rustymail-store --all-features --locked
cargo build --workspace --locked
python scripts/smoke.py
```

存储测试覆盖等长篡改、截断、追加、正常内容及目标写失败。独立 Python 实验通过真实 SMTP 接受合成邮件，停止子进程后修改临时 blob，再确认 CLI 非零退出、不打印成功记录、清理新输出并保留已有良好副本；随后恢复原文件，继续原有恢复实验。它不接触现有用户邮箱。

## 4. 固定依赖不能固定安全知识

`Cargo.lock` 固定包版本，`--locked` 阻止构建偷偷改变选择；两者都不能阻止同一版本在明天被公布漏洞。因此 [.github/workflows/security.yml](../.github/workflows/security.yml) 在 push、PR、每日 UTC 04:23 和手动触发时执行独立审计。

工作流固定 Rust 1.94.0 与 cargo-audit 0.22.2，每次从官方仓库重新取得公告，记录代码提交、锁文件摘要、工具版本和公告库提交，再执行 `cargo audit --no-fetch --deny warnings --json`。这里 `--no-fetch` 仅避免工具第二次更新刚刚克隆的数据库，并非允许使用旧缓存。漏洞或警告使任务失败；克隆、安装或扫描失败也不会标记成功。撤回版本检查保持启用。

无论扫描成功或失败，都尝试归档审计 JSON 和来源信息；没有 `continue-on-error`、过期数据库许可或漏洞忽略项。GitHub 定时任务可能延迟或被平台停用，管理员仍需关注任务是否实际运行以及失败通知。工作流提供失败状态，但仓库分支保护是否把它设为必需检查属于仓库设置，本次没有修改该设置。

命中公告时先分析并升级依赖，再运行相关回归。确需例外时，必须在审查中记录适用条件、理由、负责人和到期时间，并实现到期检查，不能永久加入无解释的忽略项。[cargo-audit 官方文档](https://github.com/rustsec/rustsec/tree/main/cargo-audit)说明了工具的扫描与忽略机制。

## 5. 自测

1. 为什么检查长度不足以发现等长篡改？答案：字节数量不约束字节内容，需要与可信摘要比较。
2. 为什么读取器已经计算哈希，调用方仍必须读到 EOF？答案：只有完成整条流并核对长度、摘要才建立成功结论。
3. 为什么无法保证错误时任意 `Write` 都没有输出？答案：流式处理必须在最终校验之前逐块交付，通用接口没有回滚能力。
4. 为什么依赖未变仍要定期扫描？答案：版本是构建输入，公告是持续更新的外部证据。
