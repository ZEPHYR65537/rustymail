## 教材的维护约定

每个新增能力同时交付：学习目标与前置知识、协议/资源不变量、源码导读、独立实验及预期响应、失败路径、验证证据和剩余限制。一个实现步骤应能回答“为什么这样做”和“怎样证明有效”，而不只是解释函数名。

区分三类表述：规范要求链接到具体 RFC 条款；项目策略说明取舍和范围；实测结论附版本、环境和原始报告。设计目标不能写成测量结果，单元测试不能写成完整互通保证，模拟断电不能写成物理掉电证明。修改行为时同步检查旧章节、README、操作手册和里程碑状态。

每次交付运行 `python scripts/check_docs.py` 检查链接与附件；语义准确性还要对照代码、测试和规范人工复核。下面 15 章是完整学习蓝图，其中 IMAP、外发、扫描和生产运维的大部分实验仍未实现。

## 学习顺序与最低前置知识

知道变量、函数、基本数据结构即可开始。先掌握 Rust 的所有权、借用、Result、迭代器、trait 和基本异步；用邮件项目把它们连接起来。遇到协议疑问查规范，遇到性能猜想做测量，遇到崩溃问题画时间线。

建议按“协议核心 → 耐久接收 → IMAP → 互联网出站 → 安全和运维”的顺序学。教程可以穿插 TCP、DNS、文件系统等基础知识，不要求先读完一本网络书才动手。

## 第 1 章：一封邮件有两个地址世界

**问题：** 邮件标题里的 From，为什么可能不是退信应该去的地址？

SMTP 信封负责这一次传输的寄件人与收件人；RFC 消息头负责给读者展示作者、收件人和内容信息。Bcc 收件人可以存在于信封而不出现在公开头部。客户端登录账号则是第三种身份。

实验：用合成报文把登录身份、MAIL FROM、From、To 和 RCPT TO 设置为不同值，在实验入口观察哪些组合被拒。实现三个独立类型，禁止一个字符串变量在不同语义之间随意复用。

要解释的反例：只验证 SMTP AUTH 成功就允许任意 From，导致本机用户冒充另一个账户；用 From 生成退信造成回弹攻击。

验收题：画出“认证账号、信封发件人、作者地址、DKIM d= 域”之间哪些是授权关系，哪些是域对齐关系。

## 第 2 章：TCP 不知道什么是命令

输入字节示例：

```text
第一次 read: EH
第二次 read: LO client\r
第三次 read: \nMAIL FROM:<a@example.com>\r\nRC
第四次 read: PT TO:<b@example.com>\r\n
```

framing 的职责是找出完整单元并保留剩余字节；业务状态机只处理完整命令。TCP 分段与应用消息边界没有对应关系。

实验：给同一条合法会话遍历所有单切分点，并随机多切分；结果必须与一次性输入相同。追加一个没有换行的巨型输入，验证内存停在预算附近而非一直增长。

Rust 知识：`&[u8]` 表示借用；当前 SMTP 使用有上限且可复用的 `Vec<u8>`，见取消与资源边界章节。未来评估 `BytesMut` 等缓冲结构时，还需考虑浅克隆会不会长期钉住巨大底层分配，不能默认换容器就节省内存。

验收题：为什么 `read_to_end` 和 `read_line(String)` 都不能直接成为通用 SMTP/IMAP 接收方案？答案需同时涉及连接生命周期、二进制 literal、编码和长度限制。

## 第 3 章：状态机比字符串分支更重要

把协议拆为 `decode(bytes) → Command`、`transition(state, command) → Actions`、`execute(actions)`。纯状态转换不打开文件、不调用 DNS，便于枚举非法路径和 fuzz。

实验：生成 DATA-before-RCPT、重复 MAIL、RSET-after-RCPT、TLS-after-pipelined-bytes 等序列，检查状态、响应、配额预约均正确。每个拒绝必须明确是否保留连接、清空事务或进入关闭态。

Rust 知识：枚举表达合法状态，newtype 区分 AccountId/Uid/SeqNo，Result 表达可恢复错误；绝不能对不可信输入使用 `unwrap()`。

验收题：错误响应已经发出，但事务中的收件人列表没清空，会怎样影响下一封邮件？

## 第 4 章：TLS、证书与信任边界

TLS 加密字节不自动保证连对服务器；证书链与主机名验证建立对端身份。STARTTLS 是同一 TCP 连接上的协议切换，需要清除旧明文阶段的安全假设。465/993 则从第一字节开始 TLS。

实验：测试正常证书、错误主机名、过期证书、未知 CA 和去掉 STARTTLS 的假服务。客户端应给出可区分的失败，不自动明文发送密码。抓包只能使用合成数据和临时凭据。

Rust 知识：用泛型或受控枚举封装明文/TLS I/O，而不是到处复制状态机；服务端证书配置可用不可变共享对象替换，但旧连接要保持可用。

验收题：为什么对个人 IMAP 连接和对互联网 MX 的 TLS 政策不能直接用同一个布尔开关？

## 第 5 章：异步让等待便宜，不让计算免费

future 在 `.await` 处让出执行机会；CPU 散列、阻塞数据库和无限解析循环仍会占住实际线程。创建任务本身也会占内存，必须在准入后再创建昂贵状态。

实验：把测试用慢同步操作错误地放进网络任务，对比 NOOP 延迟；再移入有界工作池。使用 10,000 个过载请求验证工作任务数量受限。

Rust 知识：Send/Sync、所有权转移、有界 mpsc、oneshot 回复、Semaphore permit 生命周期。等待端超时后，已经执行的 `spawn_blocking` 仍可能运行；permit 要随实际工作结束而释放。

验收题：只把所有 CPU 工作换成 `spawn_blocking`，为什么仍然可能耗光内存？

## 第 6 章：背压是资源治理

生产者快于消费者时，差额只能变成队列、被拒绝或反馈为减速。无限 channel 只是把过载延后为 OOM。

若平均到达率为 $\lambda$，平均停留时间为 $W$，稳定系统中的平均在途数量约为：

$$L = \lambda W$$

例如每秒 50 封、平均处理 0.2 秒，平均至少约 10 封处于处理中；这不是 p99 保证，也不适用于已经失稳的无界队列。扫描变慢会增加在途数，必须让上游看到背压。

实验：限制磁盘写速率，观察 ingest permit、TCP 读取、发送方耗时和临时错误；确认内存不会按传入总字节增长。

验收题：限连接数、限总字节、限并发散列与限队列长度分别防什么问题？哪个不能被其他三个替代？

## 第 7 章：什么时候真的“存好了”

写入文件、flush 用户缓冲、同步文件、rename、同步目录、数据库 COMMIT 是不同事件。应按“断电发生在下一行之前会留下什么”逐步推导。

实验：给[接收提交协议](03-storage-and-recovery.md)每一步加入 fault point，重启后核对成功应答清单与可恢复消息集合。进程被 kill 和虚拟机掉电分别测试；前者不能验证页缓存落盘。

Rust 知识：RAII 清理暂存文件，但 Drop 不是异步耐久提交机制；用类型将 Staged、Ready、Accepted 区分，减少调用方提前确认的机会。

验收题：为什么我们宁可留下 orphan 文件，也不愿数据库先引用一个还没耐久写好的文件？

## 第 8 章：事务跨不过互联网

本地事务可以原子更新队列和 UID，但无法同时原子提交“远端收信”和“本地发送状态”。远端接受后连接断开会留下无法凭空判断的窗口。

实验：假 SMTP 对端先保存消息，随后在发出最终确认前切断连接；观察发送方重试及可能重复。再在远端成功后、本地标记前终止本机。

Rust/系统知识：内部幂等键、持久队列、租约、条件更新、fencing token。它们解决的范围不同；本地 token 不能阻止远端已经发生的投递。

验收题：为什么 Message-ID 相同不足以证明两次来信应该合并？

## 第 9 章：DNS、MX、重试与缓存

DNS 不只是“域名变 IP”：MX、TXT、TTL、负缓存、临时错误和 DNSSEC 有不同语义。多个收件域的调度也需要公平，避免一个故障域占满投递池。

实验：用本机测试 DNS 提供正常 MX、优先级不同的 MX、无 MX、Null MX、NXDOMAIN、SERVFAIL、超时和私网地址。假时钟推进队列，验证正向抖动与五天到期，不让测试真的等待五天。

Rust 知识：把 Clock、Resolver 和 Connector 做为可注入的行为边界；生产仍用真实 DNS/时钟，测试用可重复结果。

验收题：为什么“没有 MX”和“显式不接收邮件”会触发不同路由？为什么检查 DNS 结果后又按域名重新连接会产生漏洞？

## 第 10 章：密码安全也有内存预算

密码散列故意昂贵，用于提高离线猜测成本。少占内存不能靠削弱散列，而应通过准入、限流、受限并发和应用密码缩小风险。

实验：测 Argon2 的单次耗时和 RSS，再测并发 1/2/8 的变化；验证未知账户请求也经过预算，撤销后旧凭据与旧会话不能继续操作。

Rust 知识：PHC 参数、随机数、secret 生命周期、避免 Debug 泄露、常量时间比较的适用边界；不能因为代码使用 `zeroize` 就承诺内存中的所有副本都消失。

验收题：JWT、OAuth、SMTP AUTH、SPF、DKIM 各自解决什么问题？为什么本项目首发不需要自己做 OAuth 服务？

## 第 11 章：MIME 是结构，不只是字符串

消息有折行头部、字符集、传输编码、多层 multipart 与附件。磁盘上的字节、解码后的文字、显示后的页面和 MIME 结构树不等价。IMAP section 偏移必须引用不可变的存储版本。

实验：纯文本、HTML alternative、中文主题、内嵌图片、嵌套 message/rfc822、畸形 boundary、过深嵌套、巨大部件数。验证正确结构与有界失败，worker 退出不拖垮主服务。

Rust 知识：借用树与拥有树的生命周期，字节范围索引，进程隔离与受限输出。不要为了简化生命周期把 25 MiB 原文无条件克隆给每个任务。

验收题：为什么 `BODY.PEEK[1]<0.1024>` 中的 1024 不能按 Unicode 字符数计算？

## 第 12 章：IMAP 是多个客户端共享的状态

初始序号 `[1,2,3]` 对应 UID `[10,11,12]`。删除第一个后，序号变成 `[1,2]`，UID 仍是 `[11,12]`。如果一个客户端继续把“2”当作 UID 11 就会操作错邮件。

实验：两个客户端同时选择同一邮箱；A 删除，B FETCH/STORE，插入第三条新信。对比客户端视图、事件序号和数据库，测试安全点通知与慢客户端断开恢复。

Rust/数据库知识：所有权检查、事务内分配 UID、版本快照、事件日志、配额和共享视图的内存代价。读事务不能跟着慢网络连接一直占用 WAL 历史。

验收题：恢复昨日备份后如果 UIDVALIDITY 不变，为什么客户端可能把新旧邮件混淆？

## 第 13 章：观察性能，不猜性能

微基准回答“某个函数多快”，端到端测试回答“给定完整工作负载下系统怎样表现”。吞吐、延迟和错误率要一起解释，平均值不能描述最慢用户。

实验：分别关闭/开启 TLS、FULL 同步、域认证、扫描；所有对照标注模式，正式生产结果不得混用。制造一个慢磁盘、一个高延迟 DNS 和一个慢收件端，学会从排队时间识别瓶颈。

工具候选：Criterion、Linux perf、火焰图、进程 RSS、cgroup、I/O 指标。优化前给出假设，优化后比较同负载数据；未改善则撤销无意义复杂度。

验收题：一个系统每秒成功发送 1000 封却拒绝 90% 请求，能否说比每秒成功 900 封且不拒绝的系统更快？还缺哪些条件？

## 第 14 章：运维是设计的一部分

从备份无法恢复、证书无法续期、队列无法解释，都会让“协议正确”失去实际意义。RPO 描述可能损失多长时间的数据；RTO 描述恢复服务需要多久，不能与 SMTP 的接受责任混为一谈。

实验：空机器恢复，旧密钥轮换，迁移失败回滚，账号被盗后 hold 队列。每个实验用真实 runbook 执行，记录文档中未预料的步骤并修订。

验收题：为什么把三个正在变化的 SQLite 文件分别复制完成，不足以证明拿到了一致快照？

## 第 15 章：在 Emacs 看见整条链路

从 Gnus 开始收信，发送含中文和附件的邮件，再检查远端头部、服务端队列、本地 Sent 和第二客户端 flags。把每个用户动作对应到协议交换，理解 MUA/MSA/MTA/MDA 的职责。

实验：发信成功后让 Sent APPEND 临时失败，保留写信 buffer，仅补归档；再制造证书错误、错误密码和超大附件。所有排错日志使用临时账号并在实验后清理。

验收题：怎样在不重复发送的情况下区分“SMTP 未接受”和“SMTP 已接受但 IMAP 归档失败”？

## 每章的交付格式

1. 学习目标及本章所需的前置知识。
2. 一张状态/数据流图，配一个可复现正常输入。
3. 两个以上真实边界或故障输入，解释错误方案为什么失败。
4. 对应源码入口与关键不变量；只引用当前真实存在的路径。
5. 可运行测试或实验命令、正常输出与异常输出、资源限制。
6. 性能和安全代价，不能只写“Rust 更快、更安全”。
7. 自测题、答案要点、规范链接和本章实际遇到的知识记录。

## 本次设计已经学到的几件事

| 发现 | 对项目的实际影响 |
| --- | --- |
| DMARC 已有 2026 年新规范 | 不把旧 RFC 7489 当成唯一基线；锁库版本后验收新规则 |
| 异步任务超时不一定结束 CPU 工作 | 散列 permit 由工作本身持有，MIME 使用进程硬限制 |
| fsync 文件不等于持久化目录项 | 提交顺序包含父目录同步，并单独做断电测试 |
| Gnus 和 SMTP 的 Sent 不是同一事务 | 客户端保留失败现场，文档提示先核实已发送状态 |
| 内存小不能只算主守护进程 | 同时报主服务、worker、Rspamd 与 cgroup 总开销 |
| 协议 parser 支持扩展不代表服务支持 | capability 由通过验收的业务能力生成 |

这些记录会随着实现被补充、修正和链接到实际代码，不将设计假设包装成已观测事实。
