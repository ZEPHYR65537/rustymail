# 安全、资源预算与性能验证

## 1. 威胁模型

| 对手或故障 | 进入点 | 必须成立的防线 |
| --- | --- | --- |
| 匿名发信者 | 25 / DATA | 收件人验证、无中继、磁盘预约、扫描和协议限制 |
| 密码猜测者 | 465 / 587 / 993 | TLS、IP 与账号双维度限流、昂贵散列并发上限 |
| 被盗账号 | 已认证提交 | send-as、速率与日配额、撤销应用密码、异常出站告警 |
| 恶意邮件 | MIME、SEARCH、FETCH | 受限解析工作进程、深度/节点/输出预算、流式正文 |
| 恶意 DNS | MX、SPF、DKIM、MTA-STS | 查询预算、SSRF 防护、缓存上限、TLS 策略 |
| 慢客户端 | TLS、DATA、IDLE、FETCH | 分阶段期限、事件/输出预算、连接数限额 |
| 本机资源故障 | ENOSPC、I/O error、OOM、断电 | 250 前耐久提交、准入拒绝、恢复扫描 |
| 有权限的操作失误 | 配置、升级、恢复、删除 | 校验、备份、审计、明确回滚路径 |

每一项至少一个集成负例。仅用 Rust 并不能防止开放中继、错误授权、资源耗尽和逻辑性丢信。

## 2. 用户认证与授权

首发使用每设备独立应用密码：随机 selector 用于查找凭据，高熵 secret 只在创建时显示一次。服务端存储 Argon2id PHC 字符串；不保存明文，不自己实现密码散列算法。创建、撤销、最后使用时间可审计。

起始 Argon2id 调参为内存 64 MiB、3 次迭代、4 lanes、随机 16 字节 salt，输出 32 字节；这是待基准校准的起点，参数和版本随 PHC 存储。部署以目标机器的认证延迟与并发内存共同决定参数，而不是照抄某个库默认值。[RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)、[RustCrypto argon2](https://docs.rs/argon2/latest/argon2/)

同时最多两个散列验证：仅这部分即可占约 128 MiB。等待队列最多 16 项，最多等待 2 秒，过载返回临时认证失败；不能无限排队，也不能为了小内存把密码验证改成快速哈希。未知账户走受限的 dummy 验证路径，限制信息泄露且避免枚举请求绕过预算。

账户撤销增加 auth_epoch、禁用相关凭据并主动结束会话；敏感操作重新验证状态，已排队但尚未发送的异常出站转 hold 等待管理员决策。密码撤销并不自动销毁之前已经接受的邮件。

send-as 权限同时约束 MAIL FROM、正文 From 与需要处理的 Sender/Resent 字段。首发仅接受单一授权 From 身份的用户提交；复杂代理和重寄通过后续明确设计支持。匿名入站不能因为正文 From 恰好属于本地域就获得任何权限。

## 3. 邮件域认证不是登录认证

SPF 检查发送主机与信封域的关系，DKIM 检查签名与内容，DMARC 结合可见发件域的对齐与域政策。它们不证明具体自然人的身份，不替代应用密码，也不能替代反垃圾分类。实现中保存各项结果和临时错误，避免把 DNS 超时当成确定的恶意邮件。

DMARC 设计以 2026 年发布的 RFC 9989 为基线；它替代了 RFC 7489 和 9091。报告规范另见 RFC 9990/9991。依赖锁定后必须验收新的政策发现与对齐规则，不能仅看到库自称“支持 DMARC”就通过。[RFC 9989](https://www.rfc-editor.org/rfc/rfc9989.html)

DKIM 默认 RSA-SHA256 2048 位，以兼容性为起点；私钥放在受限凭据文件中。轮换使用新 selector，保留旧公钥直到旧队列和传播窗口结束。禁止接受弱算法作为新签名策略。对来信验证数量、DNS 查询数、响应大小和总耗时加全局预算，超预算明确报告临时错误或策略拒绝，不产生无限计算。

Rspamd 采用本机受限访问的 `/checkv2`，传递真实连接信息和信封；正文从文件读取，不拼成第二份全量内存。只信任配置中的扫描端点，不跟随外部重定向。结果大小最多 1 MiB，超时 30 秒；过载或服务故障在最终接收前返回 451。公网生产不允许静默切换为全部放行。[Rspamd 协议](https://docs.rspamd.com/developers/protocol/)

默认 scan 2 并发，反垃圾进程的 RSS 与 CPU 单独计量；把扫描器开销排除后称整套邮件系统“只用几十 MiB”是不准确的。无扫描器仅允许封闭实验模式。

策略动作明确映射：reject 在接受前永久拒绝，soft reject/greylist 临时拒绝，允许但判为垃圾的本地邮件原子放入 Junk；no action 才走正常投递。首发不启用 Rspamd 正文改写或 body_block，未知动作或响应结构错误按临时故障处理。新增扫描结果头部在验证入站签名之后、冻结存储字节之前完成，字段长度和注入字符严格校验。账号创建同步预建 Junk 文件夹。

## 4. TLS 和直接投递策略

用户侧只启用 TLS 1.2/1.3，采用 rustls 的经过维护的密码套件集合，验证证书有效期与 SAN。握手前后均受连接和时间预算约束。客户端配置不提供“忽略所有证书错误”快捷开关。[rustls 文档](https://docs.rs/rustls/latest/rustls/)

中继侧固定主机，强制证书验证和 TLS。直接 MX 默认也优先严格验证 STARTTLS；对于没有强制政策且 TLS 不可验证或不存在的对端，首发策略为延迟重试并告警，直到到期或管理员配置明确的按域明文兼容例外。例外影响投递覆盖率和隐私，必须留审计；没有全局 `danger_accept_invalid_certs`。

实现 MTA-STS 的政策获取、验证、缓存、到期和 testing/enforce 区别；已缓存的有效 enforce 政策不能因一次拉取失败而降级。政策获取限 HTTPS 443、正文大小和时间，校验最终 IP，禁止任意 URL 跳转。[RFC 8461](https://www.rfc-editor.org/rfc/rfc8461.html)

DANE 首发暂不宣称支持。启用 DANE 的后续版本需要完整 DNSSEC 验证与 TLSA 语义，不能把普通未验证的 DNS 查询结果当成信任根；DANE 与 MTA-STS 的优先关系须独立验收。[RFC 7672](https://www.rfc-editor.org/rfc/rfc7672/)

## 5. 初始资源与超时预算

以下均为**设计初值，尚未实测**，配置以明确单位存储。

| 资源 | 默认上限 | 满额动作 |
| --- | --- | --- |
| 全局连接 | 256；单 IP 8 | 早期拒绝或短暂临时失败 |
| 单账号 IMAP 会话 | 8 | 拒绝新会话，不驱逐正常会话 |
| 并行 TLS 握手 | 16 | 有界等待/拒绝 |
| SMTP 命令 / DATA 行 | 按扩展适用的协议上限；基线 512 / 1000 字节含 CRLF | 协议错误，必要时关闭 |
| SMTP AUTH 解码数据 | 4 KiB | 立即失败，禁止按攻击者长度分配 |
| 单封原文 / 所有 headers | 25 MiB / 256 KiB | SIZE/策略错误 |
| 单事务收件人 | 100 | 后续 RCPT 返回适当错误 |
| 同时 DATA 或 APPEND | 16，共享准入 | 推迟 continuation / 临时拒绝 |
| 每流正文缓冲 | 16 KiB | 用背压等待写盘 |
| IMAP 非 literal 命令 | 16 KiB | 有界解析失败 |
| selected-view / 事件积压 | 全局 32 MiB / 每会话 64 KiB | 拒绝 SELECT / 慢会话 BYE |
| MIME 工作进程 | 1 并发，进程限 256 MiB | 超时终止并重启，接收前临时失败或明确复杂度拒绝 |
| MIME 深度 / 部件 / 输出元数据 | 32 / 5000 / 1 MiB | 拒绝复杂度超限；不能截断后假装成功 |
| DB 写队列 | 128 项，仅 ID 和有限元数据 | 限时等待 / 临时拒绝 |
| DNS / 出站 | 32 / 16 并发 | 留在持久队列 |
| 单目的域出站 | 2 并发 | 域级排队，避免压垮对端 |
| 认证散列 / 搜索 | 2 / 2 并发 | 有界等待 |
| SQLite cache | 写连接 8 MiB，读连接各 4 MiB | 总预算 16 MiB；观测真实内存 |
| 内存 DNS 缓存 | 最多 4096 项，合计不超过 8 MiB | TTL + LRU 驱逐 |
| 磁盘保留空间 | max(2 GiB, 文件系统容量 10%) | 停止新写入，允许读和队列诊断 |

SMTP 特定扩展会调整相关命令长度；不能把 512 硬套到所有 AUTH 交换。正确上限取决于解析阶段，所有放宽都写测试。

| 时间阶段 | 初始值与原因 |
| --- | --- |
| TLS 握手 | 15 秒，限制握手占用 |
| 25 端口命令空闲 | 5 分钟；不使用短 HTTP 空闲超时 |
| DATA 无进展 | 3 分钟；总接收 30 分钟，限制资源占用且保留慢网络空间 |
| 提交入口未认证空闲 | 60 秒；加密后正常 SMTP 按协议阶段管理 |
| IMAP 已认证空闲 | 35 分钟；兼顾 IDLE 和客户端保活 |
| IMAP APPEND 无进展 | 3 分钟，整体上限 30 分钟 |
| 出站 TCP / DNS | 30 / 5 秒；不含 SMTP 层等待 |
| 出站 banner、MAIL、RCPT | 每阶段 5 分钟 |
| 出站 DATA 命令 / 分块写 / 最终响应 | 2 / 3 / 10 分钟 |
| 停机宽限 | 60 秒，已开始提交优先完成；未完成网络投递可恢复 |

## 6. 内存成本模型

用预算模型解释增长，而不是只看一次 `top`：

$$M_{main} \approx M_{base} + C B_{conn} + I B_{stream} + M_{views} + M_{db} + A M_{argon2} + M_{cache}$$

其中 $C$ 是连接数，$I$ 是活动正文流数，$A$ 是并行散列数。连接含 TLS 状态、任务和发送缓冲，不能把 $B_{conn}$ 只算成 16 KiB 原文块。系统总内存还应加入 MIME worker、Rspamd、内核 socket/page cache 和其他进程。

256 条连接每条假设 64 KiB 是 16 MiB；16 条正文流各 16 KiB 仅 0.25 MiB；两个 64 MiB 散列却是 128 MiB。这解释为什么优先控制认证和解析并发，而不是先到处换无锁容器。假设值必须在测量后替换。

`mail-parser` 接收完整字节切片等 API 不能保证流式零分配。主服务从文件传给隔离 worker；worker 在操作系统内存/CPU 限额内解析并输出有界元数据。仅用同一进程的任务超时无法阻止它 OOM。具体零拷贝特性必须针对所用版本检查。[mail-parser](https://docs.rs/mail-parser/latest/mail_parser/)

文件映射也占地址空间和可能的 RSS；“mmap 所以免费”不是性能论证。TLS 下的正文传输通常需要用户态加密，不承诺传统 sendfile 零拷贝。优化先靠少复制、复用缓冲、索引、减少锁竞争和有界批处理。

## 7. 基准与目标

参考机：独立 2 vCPU、2 GiB、SSD、Linux、本地文件系统、release 构建、FULL 同步；记录 CPU 型号、存储型号/同步延迟、内核、文件系统和依赖版本。正式负载发生器在另一台机器，避免 localhost 掩盖网络或与服务器抢 CPU。

| 目标（待测） | 标准负载与指标 |
| --- | --- |
| 空闲主进程 RSS ≤ 48 MiB | 启动完成 5 分钟、无客户端、空邮件库 |
| 常态主进程 RSS ≤ 192 MiB | 100 TLS/IDLE 会话、混合收发 1 小时；扫描器/worker 另报 |
| 压力主进程 RSS ≤ 448 MiB | 达到准入限额及 2 路 Argon2；主服务硬限先设 512 MiB |
| 本地入库 ≥ 50 封/秒，p99 ≤ 500 ms | 100 KiB 原文、10 并发、TLS、FULL、1 本地收件人；排除外部扫描，单独报告 |
| 生产全链路接受 p99 ≤ 2 秒 | 相同负载，包含域认证与实际扫描；DNS 冷/热分别记录 |
| 已索引元数据 FETCH p99 ≤ 100 ms | 100,000 封文件夹，读取最近 50 封的头部元数据 |
| 正文传输内存随并发而非文件大小增长 | 1/10/25 MiB 邮件、1/8/16 流，对比 RSS 与 cgroup memory |

这些是目标，达不到应公开瓶颈与调整依据；不得为了达标改为 NORMAL 或禁用安全功能而继续称同一生产模式。

测试矩阵包含：冷/热缓存、正常/恶意 MIME、空闲/认证洪峰、单/多收件人、全部成功/4xx/超时、快/慢消费者、小/大邮箱、磁盘高水位。记录 p50/p95/p99/max、吞吐、错误率、排队时间、CPU、RSS、cgroup 内存、I/O 和 WAL 大小。

负载发生器采用可控到达率且记录被拒请求，避免只测成功请求导致 coordinated omission。先预热 5 分钟，再测 15 分钟，重复 3 次，最终 72 小时 soak。不得用 parse 微基准代替邮件接受吞吐，也不得只报平均延迟。

发布报告同时保留性能失败案例、未满足项和原始输出路径。当前没有任何实测服务器性能结果。
