# 0.3.1：取消、资源生命周期与可测量的优化

本章记录 0.3.0 复查后的修复：磁盘任务取消、撤销通知、管理响应上限，以及相关的分配和结构优化。没有新增第三方依赖，没有修改数据库 schema；L0 实验边界保持不变。

测试数量、独立客户端、原始性能与故障证据见[本轮验证报告](../reports/0.3.1/validation.md)。

## 1. 等待结束，不代表工作结束

原实现使用 Tokio 文件写入，但把磁盘额度和实例锁放在异步接收对象里。取消接收会销毁对象，文件写入却可能仍在阻塞线程执行。额度提前归还会接纳更多写入；最后一个实例锁提前释放，还可能让另一个进程在旧 I/O 未结束时打开仓库。

Rust 能阻止许多无效内存访问，但不能自动判断“许可应该等到磁盘操作结束才释放”。对于已开始的 `spawn_blocking` 工作，取消等待不能终止执行，运行时停止也可能等待它结束。[Tokio 阻塞任务约定](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html)

修复后的 [正文存储](../crates/store/src/blob.rs) 使用以下所有权关系：

```text
接收对象 ─────────┐
正在执行的磁盘工作 ─┼─ Arc<StageResources>
已准备的正文凭证 ──┘       ├─ 文件与暂存状态
                          ├─ 磁盘预留额度
                          └─ 实例独占锁
```

固定容量缓冲写满后，接收对象把缓冲和资源引用交给阻塞任务，完成后收回空缓冲。每个 stage 同时最多有一个写入或准备任务。进入可取消的操作前先标记 poisoned，完整成功后才恢复；取消后不能继续追加并用旧摘要提交。

最后一个持有者关闭文件并清理暂存路径；运行时中的清理转交阻塞线程，完成后才释放锁和额度。排队清理也消耗已有额度，不能通过反复连接和取消绕过限制。已改名的最终正文不在析构中删除：取消准备操作的等待方可能留下一份孤儿，交给已有的离线检查和 GC。

准备顺序仍为：写完缓冲、同步文件、关闭文件、改名、同步正文和暂存目录。随后数据库接受事务验证授权并完成 WAL/FULL 提交，最后才允许回复 250。结果不明的提交仍关闭连接，不当作确定失败重试。

这不保证故障磁盘上的系统调用按时返回。永久卡住的 I/O 可以延迟退出，额度继续占用；强制停止或断电也可能留下暂存文件和孤儿。恢复流程仍然必需。

### 用屏障重现，而非靠 sleep 猜调度

回归测试只给一个 stage 的额度，卡住阻塞线程，提交写入或准备工作；确认 Pending 后取消等待并销毁接收对象，断言第二个 stage 无额度、第二个 Store 拿不到锁。放行真实工作与清理后，再检查额度恢复和仓库可打开。

另一项测试卡在文件已同步、尚未改名的位置，取消外层任务再放行。最终只有无数据库引用的孤儿，已接受邮件数为零。[存储回归测试](../crates/store/src/tests.rs)与原有进程崩溃、VM 断电、真实磁盘满实验共同验证这些不同边界。

## 2. 通知消费也需要提交点

原撤销处理先等待 `watch.changed()`，再向数据库 owner 查询权限。通知已经标为已读，但若命令或 DATA 分支先完成，`select!` 会取消查询等待；下一轮又等待新通知，使已经撤销的旧会话可能继续存活。

`changed()` 自己的取消安全性不保护其完成后的应用操作。组合多个 await 时，需要逐段检查状态变化。[watch 文档](https://docs.rs/tokio/1.53.1/tokio/sync/watch/struct.Receiver.html#method.changed)、[select 取消安全性](https://docs.rs/tokio/1.53.1/tokio/macro.select.html#cancellation-safety)

新的 [Revocations](../crates/server/src/revocation.rs) 把 pending 状态放在会话里。通知到达后置为 true；仅在数据库检查完整返回且权限有效后，在没有 await 的区间清除。查询等待取消时 pending 仍在，下一轮继续检查，不需要第二次通知。查询过程中到达的更新仍留在 watch 中等待处理。

这里允许重复执行只读查询。最终接受事务的权限复查始终保留；通知负责及时断开，事务决定能否收信。回归测试卡住数据库 owner，消费通知后取消查询等待，随后不再发通知，也必须检测到撤销。

## 3. 分页数量不等于传输字节上限

凭据列表允许 100 条记录，每个标签最多 80 字节；旧版共用的 16 KiB 上限会让客户端拒绝一页合法响应。现在请求维持 16 KiB，响应为 64 KiB，均含结尾换行。

发送端通过有界对象序列化，超限时失败，完整帧准备好前不发送字节。读取最多获取上限加一字节，用于识别超限；并发、对端身份和期限限制保持不变。[管理分帧及边界测试](../crates/server/src/admin.rs)

计算上限要考虑 JSON 转义：引号和反斜杠编码为两个字节。当前标签禁止 ASCII 控制字符，80 字节标签最多使用 160 编码字节，整数按带符号 64 位最坏宽度预留。测试同时使用最大标签、ID 和时间字段。Linux 独立客户端还通过真实 Unix socket 与 CLI 验证整页，夹具在临时数据库中离线建立，不计算 100 个未使用密码的散列。

新增响应字段或放宽字符规则时，必须重算上限并更新测试。只放大读端上限而允许写端无限序列化，不构成完整修复。

## 4. 借用正文行，避免逐行分配

旧接收循环每行新建 decoder，完成时 decoder 又为下一行申请缓冲，调用者却立即销毁它。大量空行尤其容易暴露这些开销。

新 DATA 路径每封邮件建立一个 decoder，`feed_buffered` 累积有界 CRLF 帧，`frame` 借用数据，`clear` 保留容量。点透明处理只推进切片起点，不搬移后续字节。append 复制到固定流式缓冲，不持有整个邮件。命令路径仍转移小缓冲所有权，便于 AUTH 独立清理秘密。

这不是端到端零复制：TLS、网络和磁盘缓冲仍有复制。目标是去掉多余分配，保留 CR/LF 分片、NUL、1000 字节解码行长和额外透明点校验。[协议实现](../crates/protocol/src/lib.rs)

```sh
cargo run -p rustymail-protocol --example framing --release --locked
```

实验对 2、80、1000 字节行分别处理约 16 MiB，四轮交替测量顺序。比较的是同一新版本二进制中的拥有缓冲 API 和借用 API；旧版的多余下一行分配已移除，不能把结果称为完整旧版到新版加速比。它也不包含 TLS、Argon2 或磁盘同步。完整匿名收信基准仍由 `scripts/benchmark.py` 提供。

## 5. 组合预算、日志与结构整理

Argon2 默认仍是每任务 64 MiB、两路并发。新增组合检查要求配置内存乘并发不超过 256 MiB。线程栈、SQLite、TLS、连接缓冲都在此之外；密码散列预算不是总 RSS，M1 匿名收信数据也不能代替登录高峰测量。

速率表仍分别最多 4096 个 IP 和账号，窗口 60 秒。全表过期扫描改为最多每秒一次；访问到的记录单独判断到期，所以不会因此延长账号窗口。表满时，新键可能保守等待下一次清理，不挤掉有效计数。

诊断日志采用独立线程和 128 项队列，每条编码记录最多 8 KiB。满队列或输出失败累计丢失数，恢复后在后续写入时报告 `logs_dropped`。队列最多保留 1 MiB 编码内容；实际内存还有 String 容量、对象和线程栈。正常退出最多等两秒排空；永久阻塞、强杀或断电可能丢日志。它不是持久审计账本，邮件接受责任和 GC 审计仍以数据库为准。[日志实现](../crates/server/src/logging.rs)

结构调整保持有限：SASL 对话拆成专用模块，普通数据库调用复用已有通道，接受操作保留表达结果不明的专用路径；短命 CLI 改用单线程异步调度器。没有为减少行数把在线/离线的不同安全边界塞进统一框架。

## 6. 保留的限制与学习练习

启动和每次 GC 仍读取全部已引用正文并校验 SHA-256。内存为流式，耗时却随全部正文增长；`gc --limit 1` 只限制候选数量，不限制前置校验。本轮没有简单跳过检查。

生产前须设计快速启动与有界后台校验：哪些元数据和引用必须先通过，未经本轮散列的正文是否可读，损坏如何隔离，扫描如何续跑和限制 I/O。策略及恢复实验完成后，才能更改全量扫描。大存量启动延迟、TLS/认证混合负载 RSS 和长期压力仍须单独验收。

读者练习：在每个 await 处画出资源归属；用屏障重现一次取消；分别写出分页、日志和认证的数量预算与字节预算。答案要点是让额度覆盖真实工作的生命周期、把跨取消状态保存在会话中、按编码后的最坏大小计算上限。测试提供证据，不证明整个程序永远无漏洞或不会耗尽资源。
