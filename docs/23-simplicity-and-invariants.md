# 精简设计：保留不变量，删除没有使用者的兼容负担

本章记录 2026-10-08 的开发阶段整理。目标是在首次正式发布前只维护当前行为，减少重复状态与分支，同时保持邮件接受、配额、权限和恢复语义。它没有增加新的生产能力；项目仍为 L0 实验服务器。

前置阅读：[本地持久化](11-m1-storage.md)、[取消与资源生命周期](13-cancellation-and-bounds.md)、[失败通知](22-m43-delivery-lifecycle.md)。

## 1. 先确定真正需要兼容的对象

正式发布后的数据库升级要对已有用户数据负责；开发阶段每次修改表结构，并不自动形成长期支持一个实验版本的义务。

此前程序保存四代 SQL、迁移历史、SQL 摘要与旧格式转换规则。测试又把新数据库重建成旧数据库，再验证升级回来。这些代码服务于早期实验库的兼容性，增加了每次改动的理解和验证成本。

当前只维护一份 [schema.sql](../crates/store/schema.sql)。业务表、约束及必要索引直接写在这里；教程不再保留另一份可执行 SQL 草案。删除了迁移历史表、查询命令、旧结构修复分支和专用降级 fixture。尚未生成实际内容的 MIME 元数据及其版本占位列也已删除，解析功能实现时再定义。Git 历史与历史验证报告仍可用于学习当时的方案。

**不兼容的实验库会被拒绝打开，程序不会自动清空或转换它。** 需要保留已有数据时，使用对应旧提交的程序完成导出或一致备份，再为当前程序选择一个新数据目录。不要手改数据库标记来绕过检查。正式发布前再确定稳定格式和真实需要支持的升级路径。

## 2. 删除迁移链后，初始化仍需事务

[schema.rs](../crates/store/src/schema.rs)处理三种情况：

| 数据库 | 行为 |
| --- | --- |
| 完全空的数据库，调用允许创建 | 在一个事务内创建全部对象及 application_id 标记 |
| 标记和结构均匹配当前定义 | 正常打开 |
| 旧实验库、其他应用的库、结构被修改或不完整 | 返回错误，保留原内容 |

application_id 只识别文件归属，不代表发布日期。结构检查同时比较表、索引、视图和触发器，不能仅凭一个数字宣布数据库兼容。客户端和服务端配置中的固定 `schema_version = 1` 也已删除；当前字段、类型和取值校验负责拒绝无效配置，不维护旧版本转换逻辑。

初始化中途失败时，事务回滚到空库；COMMIT 后响应丢失时，磁盘上可能已有完整结构，必须重开确认。两种情况都不能留下只有一半业务表的“成功数据库”。检查已有库的接口不初始化空库，避免路径或文件错误被掩盖。

这些保证与“支持多少个旧版本”无关，因此保留相应的故障点和测试。

## 3. 公共事务比复制业务 SQL 更容易保持正确

普通邮件与失败通知都需要向本地邮箱添加一份投递，原来各自维护接收权限、UID、邮箱事件和配额规则。现在两条路径共同调用 [local_delivery.rs](../crates/store/src/local_delivery.rs)。

一次本地投递在调用方的事务内完成：

1. 查询有效接收地址、活动账号、INBOX、当前 UID/event_seq 和已用配额。
2. 检查计数器没有耗尽，增加本封邮件后不超过配额及整数范围。
3. 写入 delivery、mailbox_message、邮箱事件，增加计数器和账号已用空间。

多个别名指向同一邮箱时，后一次读取能看到同一事务中前一次的计数器和配额更新。任何收件人失败都会回滚整个接受事务，包括此前成功处理的收件人和远端投递责任。不存在先返回部分本地成功、再报整体失败的路径。

固定 SQL 使用连接内有界语句缓存复用准备结果；正文仍流式写入文件，不进入这个元数据函数。

失败通知在生成文件前仍做一次配额预检，以减少明显无法投递时产生的孤立文件；最终提交仍重新校验，因为两者之间账号、配额或其他邮件可能变化。它们位于不同的并发时间点，不能因外观相似而删除后一次检查。

## 4. 统一管理行为，保留执行环境的区别

[AdminRequest::apply](../crates/server/src/admin.rs)定义唯一的业务处理与返回结构。离线 CLI 直接使用独占打开的 Store；在线请求交给数据库所有者线程。昂贵的 Argon2 生成留在数据库线程之外，并先验证便宜的输入条件。

在线权限变更还必须通知现有会话。通知与数据库操作在同一所有者任务里完成，即使请求者取消等待也不会漏掉。离线命令没有活动会话，因此不需要这个通知。这项差异保留在调用方，而不再复制账号和凭据操作。

实际修复的差异是 `send-as`：在线和离线都返回 `account_id` 与 `enabled`。独立 Unix socket 实验比较两者结果，并继续验证撤销会使旧会话失效。

## 5. 有界调度还必须考虑公平性

旧实现把首次通知的 `notification_due_ms` 设为 `0`，失败重试则设为当前时间加 60 秒。索引按这个字段排序，因此持续出现的新失败永远排在已经到期的重试前面。限制每秒一个任务控制了资源，却没有保证旧任务能获得机会。

现在，永久失败和到期处理都把首次通知时间设置为发生终态的时间；重试仍使用实际的下一次可执行时间。已到期重试会排在后来发生的新失败前面。索引仍是 `(notification_due_ms,id)`，一次只选择一项，内存和扫描范围保持有界。

还要处理时钟跳变：已知的 SMTP 结果必须保存，但不能用异常地跳到明天的时间推迟报告。时钟异常时保留最后一次通过检查的通知时间，停止新调度；校正时钟并重启后再恢复。测试分别覆盖新 SMTP 失败、新到期任务，以及已知结果记录期间的时钟跳变。

## 6. 配置与索引也会形成维护负担

删除尚未接入的 IMAP、MIME worker、反垃圾、直接 MX、DNS 缓存、指标和读线程配置；它们的目标设计仍保留在架构章节，实现时再加入真实接口。日志固定为有界且不含秘密的 JSON，存储固定 WAL/FULL、离线 GC，无需通过配置重复声明不可变策略。未知键继续报错，不会静默忽略旧配置。

统一程序只构建 `rustymail`，不再保留 `rustymaild`、`rustymailctl` 和重复的参数转换。脚本及服务模板同步使用 `send`、`serve`、`admin`、`check`。

旧全量 `delivery_due`、`delivery_domain` 索引也已删除：当前扫描使用专用部分索引，域并发从有界的活动任务集合统计。这减少持久化索引和写入维护，不代表邮件吞吐已经提高某个百分比。

## 7. 如何验证精简没有改变责任边界

运行以下检查；所有协议实验使用临时目录、合成账号及环回对端：

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test --workspace --all-features --locked
cargo build --workspace --all-targets --all-features --locked
python scripts/check_docs.py
python scripts/smoke.py
python scripts/m2_smoke.py
python scripts/m41_smoke.py
python scripts/m43_smoke.py
python scripts/cli_smoke.py
```

Windows 不覆盖 Unix 管理 socket 和目录同步；Linux 回归继续验证这些路径。VM 故障脚本先持久化私有空库及其目录项，再在首次 SQLite 初始化提交前后中断，以单独检验事务边界；邮件提交和 GC 场景继续保留。历史报告不会被改写成新实现的测量结果。

练习：为两个指向同一邮箱的别名设置“只够一份邮件”的配额；解释整个接受事务为什么必须回滚。再构造一个配额恢复后的通知重试与一个新失败，观察它们的调度顺序。最后在当前数据库删除一个必要索引，确认程序拒绝打开且未重建或清空已有数据。

代码量减少是维护收益的证据。吞吐、尾延迟和运行时内存仍需要在对应版本及负载上测量；事务复核、EOF 完整性校验、取消后的资源令牌和队列未知状态都有独立职责，继续保留。
